Stockage SQLite

L’application conserve les connaissances et les scripts dans un même fichier SQLite : data/memory.sqlite par défaut. La variable MEMORY_DB permet de choisir un autre chemin. Les données sont conservées entre les exécutions et les redémarrages.

Le schéma comporte onze tables. compositions et phrases contiennent les faits ; refs et primitive_values fournissent les domaines de valeurs utilisés par les requêtes. Complement indexe les compléments ordonnés de chaque phrase. fact_arguments relie chaque fait à ses références et valeurs. saved_scripts conserve les programmes de la console. agent_calls conserve les appels exécutés pour l’agent.

Le serveur initialise les onze tables au démarrage, dont les trois dictionnaires lexique_verbes, lexique_noms_communs et lexique_prepositions. La source structure-langage-pour-ia.ts présentée à l’agent est une référence avec mémoire en RAM ; l’exécution par l’API utilise ce stockage SQLite.

refs — identités des entités

Chaque entité possède une identité Ref, généralement un UUID. Son nom, son type et ses propriétés sont enregistrés séparément dans les compositions.

Colonnes de refs
ColonneType et contrainteContenu
valueTEXT, clé primaireRéférence sérialisée, par exemple {"$ref":"uuid-alice"}.

Une référence est ajoutée automatiquement lorsqu’elle apparaît dans un fait enregistré, y compris dans une proposition imbriquée. new Ref() seul ne l’enregistre pas. Les insertions répétées de la même identité sont ignorées. Cette table sert de domaine aux variables de type "Ref".

compositions — types, noms et propriétés

addMemoryComposition(ref, name, of?) crée une ligne. Par exemple, addMemoryComposition(alice, "Personne") attribue un type à Alice ; addMemoryComposition("Alice", "Nom", alice) lui attribue un nom.

Colonnes de compositions
ColonneType et contrainteContenu
idINTEGER, clé primaireIdentifiant technique de la ligne, attribué par SQLite.
refTEXT, NOT NULLPremier argument sérialisé : référence, valeur primitive ou expression.
nameTEXT, NOT NULLNom commun en texte brut, par exemple Nom, sans guillemets JSON.
qualifierTEXT, nullableQualificatif en texte brut, ou SQL NULL si le nom est simple.
of_valueTEXT, NOT NULLArgument of sérialisé ; {"$undefined":true} lorsqu’il est absent.
valueTEXT, NOT NULLComposition complète au format {"$composition":[ref,name,of]}.

Les colonnes séparées permettent de rechercher les faits avec est(...). La colonne value permet de reconstruire un objet Composition.

Index : comp_lookup(name, ref, of_value, qualifier) et comp_reverse(name, of_value, ref, qualifier).

phrases — actions, relations et propositions

phrase(subject, name, ...complements) construit le tuple ["phrase", subject, name, ...complements], sans écriture. addMemoryPhrase enregistre ce tuple comme affirmation indépendante et crée aussi les lignes de ses phrases imbriquées. Le sujet peut être absent et les compléments peuvent contenir des références, des nombres, des booléens ou des propositions imbriquées.

Colonnes de phrases
ColonneType et contrainteContenu
idINTEGER, clé primaireIdentifiant technique de la ligne, distinct de l’identité d’une entité.
subjectTEXT, NOT NULLSujet sérialisé, ou marqueur {"$undefined":true}.
nameTEXT, NOT NULLVerbe en texte brut, par exemple roule, sans guillemets JSON.
qualifierTEXT, nullableQualificatif en texte brut : ["roule", "très vite"] devient name = roule et qualifier = très vite. Un nom simple a un qualificatif SQL NULL.
complementsTEXT, NOT NULLTableau JSON ordonné des compléments, par exemple [["à",{"$ref":"uuid-bob"}]].
valueTEXT, NOT NULLTuple complet au format ["phrase",subject,name,...complements].
owner_typeTEXT, nullableSQL NULL pour une affirmation indépendante ; phrase ou composition pour une phrase contenue dans un autre fait.
owner_idINTEGER, nullableIdentifiant du fait contenant ; SQL NULL pour une affirmation indépendante.

Les recherches phrase(...) utilisent les colonnes séparées et sélectionnent les affirmations indépendantes (owner_type IS NULL). Le domaine des variables "Phrase" contient tous les tuples stockés, y compris imbriqués. Chaque contenu distinct possède une ligne par fait contenant, également lorsqu’il figure dans une composition ou dans une négation. Les anciennes représentations sont converties automatiquement, sans supprimer les faits ni changer leurs identifiants.

Index : phrase_lookup(name, subject, complements, qualifier), phrase_reverse(name, complements, subject, qualifier) et phrase_owner(owner_type, owner_id). Les déclencheurs compositions_delete_phrases et phrases_delete_phrases suppriment les lignes dépendantes lors du nettoyage du contenant.

Par exemple, « Alice pense que Bob dort » crée une ligne indépendante pour la croyance d’Alice et une ligne rattachée pour le contenu « Bob dort ». La seconde conserve ce contexte et ne rend pas phrase(bob, "dort") vrai en dehors de la croyance.

Dictionnaires français

lexique_verbes contient 88 811 formes verbales, conjugaisons comprises ; lexique_noms_communs, 43 654 noms singuliers ou invariables ; lexique_prepositions, 140 prépositions et locutions ainsi que 8 conjonctions déjà utilisées avec les propositions. Les colonnes sont mot (TEXT, clé primaire), source (TEXT) et nature (TEXT). La troisième table distingue prépositions et conjonctions par la colonne nature.

Les données sont incluses dans src/lexicon/ et chargées sans réseau à l’ouverture de la base. Les formes verbales et noms sont extraits de Lexique 4.15, sous CC BY-SA 4.0 ; le dépôt conserve licence et provenance. La liste est finie et peut manquer certains termes. Pour régénérer : python3 scripts/import-lexicon.py, puis npm run build.

Un verbe ou une forme verbale inconnue, un nom inconnu ou une préposition absente provoque une erreur dans les insertions et requêtes, y compris imbriquées. Les phrases utilisent une forme conjuguée adaptée au texte, par exemple phrase(p, "mange") ou phrase(p, "travaillait"). Les prédicats sont comparés exactement, sans lemmatisation implicite. Les anciennes bases sont automatiquement enrichies avec les conjugaisons. L’API renvoie HTTP 400 avec le mot et la table concernés ; les écritures de l’appel sont annulées. Les noms propres et valeurs textuelles restent libres. Les qualificatifs n’ont pas de table dédiée. Les dictionnaires sont conservés par la RAZ.

SELECT mot FROM lexique_verbes WHERE mot LIKE 'mang%';
SELECT mot FROM lexique_noms_communs WHERE mot LIKE 'person%';
SELECT mot, nature FROM lexique_prepositions ORDER BY mot;

primitive_values — domaine des valeurs primitives

Cette table répertorie les chaînes, nombres et booléens rencontrés dans les arguments des faits, y compris les propositions imbriquées. Elle fournit les domaines des variables "string", "number" et "boolean".

Colonnes de primitive_values
ColonneType et contrainteContenu
typeTEXT, NOT NULLType JavaScript : string, number ou boolean.
valueTEXT, NOT NULLValeur JSON : "Alice", 32, true, etc.

La clé primaire composée (type, value) élimine les doublons. Le nombre 32 et la chaîne "32" sont distincts. Les noms de prédicats, rôles et variables ne font pas partie de ce domaine.

Cette table ne décrit pas à qui appartient une valeur : ce lien est conservé dans le fait. Si elle manque dans une ancienne base, le runtime la crée et la remplit à partir des compositions et phrases existantes, dans une transaction.

Complement — compléments ordonnés des phrases

Chaque complément d’une phrase mémorisée possède une ligne. Les doublons sont conservés et une phrase sans complément n’ajoute aucune ligne. Une phrase imbriquée reste une valeur JSON dans Element.

Une chaîne est interdite comme valeur de complément : ni "rapport" ni ["objet", "rapport"] ne sont autorisés. Le mot-clé reste du texte ; la valeur désigne une entité par sa Ref. Par exemple : const objet = new Ref(); addMemoryComposition(objet, "Rapport"); addMemoryPhrase(auteur, "envoie", objet);. Les textes descriptifs sont enregistrés dans les compositions. Les variables string sont également refusées dans une position de complément ; nombres, booléens, phrases et propositions restent autorisés.

Colonnes de Complement
ColonneType et contrainteContenu
idPhraseINTEGER, NOT NULLIdentifiant dans phrases.
ordreINTEGER, NOT NULLPosition du complément, à partir de 0.
motClefTEXT, nullableRôle en texte brut, par exemple à ; SQL NULL pour un élément nu.
ElementTEXT, NOT NULLValeur encodée en JSON, sans le mot-clef.

Le complément direct, notamment le COD, n’a pas de mot-clé : « envoie un rapport à Clara » devient phrase(auteur, "envoie", rapport, ["à", clara]). Un couple conserve le mot de liaison naturel : à, sur, pour, avec, depuis, etc. Le type Preposition est une chaîne documentée ; le moteur exige un mot de liaison présent dans lexique_prepositions. Ne pas ajouter un rôle objet à une référence directe.

La clé primaire est (idPhrase, ordre). L’index complement_lookup(idPhrase, motClef, Element) permet de rechercher un complément exact. La migration remplit cette table à partir des phrases existantes. Les écritures et suppressions sont transactionnelles ; le déclencheur phrases_delete_complements nettoie les lignes d’une phrase supprimée.

Une variable de type "complements" parcourt les listes de phrases.complements, y compris les listes vides et celles des phrases imbriquées. Dans phrase, elle représente la liste entière. contient teste la présence d’un couple exact ou d’un élément nu, indépendamment de sa position et des autres compléments :

print(query(select({ p: "Ref", c: "complements", dest: "Ref" }, and(
    phrase(variable("p"), "donne", variable("c")),
    contient(variable("c"), ["à", variable("dest")])
))));

Les formes ["phrase", sujet, verbe, ["var", "c"]] et ["contient", ["var", "c"], [motClef, element]] sont également disponibles. contient accepte une liste littérale. Avec un autre type de variable, le dernier argument de phrase reste un complément unique.

fact_arguments — retrouver les faits liés à une référence

Cette table indexe les références et les valeurs primitives contenues dans chaque fait, y compris dans les compléments et les propositions imbriquées. Une même valeur répétée dans un fait n’y figure qu’une fois.

Colonnes de fact_arguments
ColonneType et contrainteContenu
typeTEXT, NOT NULL, CHECKRef, string, number ou boolean.
valueTEXT, NOT NULLRéférence ou valeur encodée en JSON, au même format que dans les répertoires.
fact_typeTEXT, NOT NULL, CHECKcomposition ou phrase.
fact_idINTEGER, NOT NULLIdentifiant de la ligne dans compositions ou phrases, selon le type de fait.

La clé primaire (type, value, fact_type, fact_id) permet de retrouver les faits qui mentionnent une référence sans parcourir tous leurs JSON. L’index fact_arguments_by_fact(fact_type, fact_id, type, value) retrouve les arguments d’un fait. Les noms de prédicats, qualificatifs, rôles et variables sont exclus de cet index.

Les insertions de faits, les répertoires et cet index sont mis à jour dans une même transaction. Les déclencheurs compositions_delete_arguments et phrases_delete_arguments retirent les entrées d’index lorsqu’un fait est supprimé. À la première ouverture d’une ancienne base, cet index est construit à partir des faits existants.

Dans les résultats de la console TypeScript, une case à cocher accompagne chaque référence reconnue, y compris dans un objet imbriqué ou une chaîne JSON. Les références de l’exécuteur sous la forme {"id":"…"} sont également reconnues. Les occurrences d’une même référence partagent leur sélection.

Les commandes Tout sélectionner, Tout désélectionner et Supprimer la sélection agissent sur la sortie courante. Elles sont désactivées en lecture seule. Revenir en lecture seule, effacer les résultats ou lancer une nouvelle exécution réinitialise la sélection et annule tout aperçu encore en cours.

L’aperçu indique le nombre de compositions et phrases concernées avant confirmation. Les faits partagés entre plusieurs références sélectionnées sont comptés une seule fois. La suppression de toute la sélection s’effectue dans une seule transaction : une erreur annule l’ensemble.

Les faits complets qui contiennent les références sélectionnées sont supprimés. Les autres faits sont conservés. Les références et valeurs primitives qui ne sont plus utilisées par aucun fait sont retirées des répertoires. La sortie de console reste une copie des résultats précédents ; relancer une lecture l’actualise.

POST /api/refs/preview accepte {"refIds":["id-1","id-2"]}. POST /api/refs/delete exige {"refIds":["id-1","id-2"],"mode":"write"} ; le mode lecture ou l’absence de mode renvoie HTTP 403. Les routes individuelles GET /api/refs/:id et DELETE /api/refs/:id restent disponibles.

saved_scripts — programmes enregistrés dans la console

Les routes /api/scripts et /api/scripts/:id enregistrent et rechargent les programmes de l’éditeur. Enregistrer un script conserve son code sans l’exécuter.

Colonnes de saved_scripts
ColonneType et contrainteContenu
idTEXT, clé primaireUUID du script.
nameTEXT, NOT NULL, UNIQUENom choisi dans la console.
codeTEXT, NOT NULLCode TypeScript sous forme de texte.
modeTEXT, NOT NULL, CHECKValeur limitée à read ou write.
typeTEXT, NOT NULL, CHECK, DEFAULT 'utilisateur'exemple pour les modèles fournis ; utilisateur pour les scripts créés ou clonés. Les scripts existants deviennent utilisateur lors de la migration.
updated_atTEXT, NOT NULLDate ISO de création ou de dernière modification ; exposée sous le nom updatedAt dans l’API.

L’onglet Script affiche uniquement les scripts de type utilisateur ; l’onglet Exemple affiche les scripts préinstallés de type exemple. Changer d’onglet conserve le code courant. Le nom et le code d’un exemple chargé sont en lecture seule. Pour les modifier, cliquer sur Cloner : la copie de type utilisateur s’ouvre dans Script.

Le catalogue contient 25 scripts, ajoutés automatiquement sans exécution, couvrant les booléens, est, phrase, eq, not, and, or, implies, contient, all, exists et switchCase. Chaque script est autonome et sans définition de fonction : il crée ses données privées, affiche son résultat attendu puis les supprime dans finally avec deleteReferences. Aucun autre exemple n’est requis. Les données temporaires nécessitent le mode écriture ; les booléens seuls restent en lecture. Les exemples sont idempotents et préservent les données préexistantes, même homonymes. Les scripts restent présents après une RAZ. Supprimer retire un script utilisateur après confirmation ; l’API DELETE /api/scripts/:id refuse la suppression d’un exemple (HTTP 403).

Le scénario Exemple traductions complexes comprend une insertion et neuf requêtes : jointures, cause et compléments multiples, croyances et provenance, quantificateurs imbriqués, négation et absence, décisions avec exceptions, valeurs typées et temps verbaux. Chaque requête décrit le texte naturel, sa traduction et le résultat attendu ; les scripts peuvent être exécutés dans n’importe quel ordre. L’annexe de l’agent est générée depuis ce catalogue par npm run build ; elle utilise donc les mêmes scripts autonomes que la console. Les données fictives ne sont pas insérées automatiquement.

Le bouton Cloner enregistre le code et le mode courants dans une nouvelle ligne, avec un nouvel UUID et un nom disponible (« Nom — copie », « Nom — copie 2 », etc.), puis charge cette copie. Le script d’origine est conservé et le code n’est pas exécuté. Une modification avec Enregistrer remplace le nom, le code et le mode des scripts utilisateur en conservant l’UUID ; les exemples d’origine sont protégés. Il n’y a pas d’historique de versions. SQLite crée les index associés à la clé primaire et au nom unique.

agent_calls — texte source, code traduit et réponse

La console utilise POST /api/execute sans historique. L’agent utilise POST /api/agent/execute avec {source, code, mode} : le texte source naturel est obligatoire, même en lecture. Le serveur exécute le code traduit fourni par l’agent.

Colonnes de agent_calls
ColonneTypeContenu
idTEXT, clé primaireIdentifiant UUID renvoyé sous callId.
created_at, completed_atTEXTDates ISO de début et de fin ; la fin est absente pendant l’exécution.
sourceTEXT, NOT NULLQuestion ou fragment de document en langage naturel, conservé tel que reçu.
codeTEXT, NOT NULLTraduction TypeScript exécutée.
modeTEXT, NOT NULLread ou write.
statusTEXT, NOT NULLrunning, succeeded ou failed.
http_status, duration_msINTEGERStatut HTTP et durée en millisecondes, renseignés à la fin.
responseTEXTRéponse JSON, y compris les erreurs ; absente pendant l’exécution.

Un index trie les appels par date et identifiant décroissants. L’appel est inscrit avant l’exécution et finalisé après la sortie du processus. Le journal est conservé même si une erreur annule les faits du script. Les requêtes invalides et les refus pour service occupé ne sont pas exécutés et ne créent pas de ligne.

L’onglet Historique agent propose une liste paginée et le détail de chaque appel. Les API GET /api/agent/calls?limit=25&offset=0 et GET /api/agent/calls/:id permettent aussi sa consultation.

Le bouton RAZ vide les tables de mémoire et cet historique après confirmation. Les trois dictionnaires sont conservés. La table saved_scripts est également exclue : les scripts enregistrés dans l’interface web sont conservés, avec leurs identifiants, noms, codes, modes et dates. Il appelle POST /api/database/reset avec {"confirm":"RAZ"}. La remise à zéro est atomique et conserve le schéma ; elle est refusée pendant une exécution. Le script chargé, sa sélection et les modifications non enregistrées dans Monaco restent disponibles ; les scripts peuvent être rechargés, modifiés ou exécutés après la RAZ.

Format JSON des données sémantiques

Les colonnes name et qualifier des compositions et phrases contiennent du texte brut. Les arguments et les objets complets restent encodés en JSON : même un nombre ou un booléen y est stocké comme texte JSON, puis retrouve son type JavaScript à la lecture. Le code et les métadonnées de saved_scripts sont du texte ordinaire.

Pour filtrer un nom dans l’onglet Base SQLite, écrire directement WHERE name = 'Personne'. Ce filtre inclut les formes qualifiées ; ajouter AND qualifier IS NULL pour demander uniquement le nom simple, ou AND qualifier = 'très vite' pour un qualificatif précis. Le runtime conserve cette distinction dans les requêtes est et phrase.

Les anciennes bases sont converties automatiquement à l’ouverture : le nom et le qualificatif sont extraits du JSON complet, et les index sont actualisés dans une transaction. Le JSON complet conserve le nom d’origine, sous forme de chaîne ou de couple.

Marqueurs de sérialisation
Valeur JavaScriptReprésentation JSON
Référence{"$ref":"uuid"}
undefined{"$undefined":true}, distinct de SQL NULL.
Composition{"$composition":[ref,name,of]}
Phrase["phrase",subject,name,...complements]
Expression, rôle, qualificatifTableau JSON, par exemple ["est",{"$ref":"uuid"},"Personne"].
Valeur primitive"Alice", 32 ou true.

Les liens sémantiques entre faits passent par les références encodées. Complement.idPhrase déclare une clé étrangère vers phrases.id ; un déclencheur assure aussi son nettoyage. Les noms et les listes complètes de compléments sont comparés structurellement ; leur ordre et leurs qualificatifs comptent.

Exemple : enregistrer Alice et son âge

Dans la console, exécuter ce script en mode écriture :

const alice = new Ref();
addMemoryComposition(alice, "Personne");
addMemoryComposition("Alice", "Nom", alice);
addMemoryComposition(32, "Age", alice);
addMemoryPhrase(alice, "dort");

Sur une base vide, cela ajoute une référence dans refs, trois lignes dans compositions, une ligne dans phrases, six liens dans fact_arguments et deux valeurs dans primitive_values : (string, "Alice") et (number, 32). Les noms Personne, Nom, Age et dort restent dans les faits.

Pour la ligne correspondant au nom, en remplaçant l’UUID généré par uuid-alice pour la lecture :

ref      = "Alice"
name     = Nom
qualifier = NULL
of_value = {"$ref":"uuid-alice"}
value    = {"$composition":["Alice","Nom",{"$ref":"uuid-alice"}]}

Le nom et l’âge se recherchent ensuite sans connaître les tables :

print(query(select({ p: "Ref", age: "number" }, and(
    est("Alice", "Nom", variable("p")),
    est(variable("age"), "Age", variable("p"))
))));

Réexécuter le script de création génère une nouvelle identité. Pour enrichir une personne existante, retrouver d’abord sa référence et vérifier qu’il s’agit de la bonne entité.

Requêtes, transactions et limites du stockage

query(select(...)) est compilé en SQL paramétré. Les domaines des variables utilisées viennent de refs, phrases ou primitive_values selon le type déclaré ; les conditions est et phrase consultent les tables de faits. Les résultats sont décodés en objets et valeurs JavaScript.

Une variable déclarée dans select mais inutilisée dans la condition vaut undefined. Son domaine n’est pas parcouru, même s’il est rempli ; un domaine vide n’empêche donc pas les autres résultats. Par exemple, select({p:"Ref",n:"string"},est(variable("p"),"Personne")) renvoie les personnes avec n: undefined. Une variable masquée par un quantificateur ne lie pas la variable extérieure.

Une condition true ne lie aucune variable. Pour lister toutes les chaînes enregistrées, écrire query(select({n:"string"},eq(variable("n"),variable("n")))). Les variables réellement utilisées et les domaines locaux des quantificateurs conservent leurs conditions habituelles.

Le runtime retourne de vrais undefined. Dans le JSON de l’API, les propriétés correspondantes sont encodées {"$undefined":true} pour conserver les colonnes ; la console les affiche comme undefined.

Les scripts des deux API d’exécution s’effectuent dans une transaction : une erreur annule leurs écritures, y compris les références et les valeurs primitives ajoutées. L’historique d’un appel agent est enregistré séparément et conserve l’erreur. Les connexions utilisent le journal WAL et un délai d’attente SQLite de 5 secondes. Les fichiers annexes -wal et -shm appartiennent à SQLite ; ce ne sont pas des tables applicatives.

Les tables de faits n’ont pas de contrainte d’unicité sémantique : enregistrer deux fois la même composition ou la même phrase crée deux lignes. L’application ne fusionne pas automatiquement les entités et n’infère pas de nouveaux faits. Les tables de faits ne possèdent pas de colonnes dédiées à la date, à la source ou à l’auteur ; ces informations doivent être représentées explicitement par des compositions et des phrases lorsqu’elles sont nécessaires.

Schéma et sérialisation définis dans src/runtime.ts ; stockage des scripts dans src/scripts.ts.
